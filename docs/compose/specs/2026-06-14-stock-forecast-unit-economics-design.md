## [S1] Контекст и цели

### Проблема
Текущий дашборд WB Sync показывает оперативные данные (остатки, заказы, продажи, реклама), но не даёт:
- Прогноза того, когда товары закончатся на складе
- Понимания реальной прибыльности каждого SKU после вычета всех расходов

### Цели
1. **Прогноз остатков** — предсказать дату запаса по каждому товару на горизонте 30 дней
2. **Юнит-экономика** — рассчитать чистую прибыль, маржинальность, ROMI, CPA, LTV по каждому SKU

### Методология
- Server-side расчёт: вся логика на Python, фронтенд только отображает
- Данные из существующих таблиц: `Stock`, `Sale`, `Order`, `SalesReport`, `ShelfMetric`, `AdCampaignStats`

## [S2] Прогноз остатков — Методология

### Алгоритм

1. **Расчёт средней скорости продаж (velocity):**
   - Берём историю продаж за последние 30 дней из `Sale` таблицы
   - Считаем среднее количество продаж в день по каждому `nm_id`
   - Учитываем тренд (рост/снижение) через линейную регрессию

2. **Прогноз потребления:**
   - `forecast[d] = velocity * (1 + trend * d)` — дневное потребление с учётом тренда
   - Суммарное потребление за 30 дней: `total_consumption = sum(forecast[d] for d in 1..30)`

3. **Остатки на начало прогноза:**
   - Текущий остаток из `Stock` (quantity + in_way_to_client)
   - Вычитаем `in_way_from_client` (возвраты в пути)

4. **Дни до заполнения (Days of Stock - DOS):**
   - `DOS = current_stock / velocity`
   - Цветовая индикация: 🔴 < 7 дней, 🟡 7-14 дней, 🟢 > 14 дней

5. **Прогнозная кривая:**
   - Построение линии остатков на 30 дней вперёд
   - Точка пересечения с нулём — дата预计ного запаса

## [S3] Юнит-экономика — Методология

### Структура расчёта

```
Выручка = retail_price_withdisc_rub × quantity_sold
                    ↓
    ┌───────────────┴───────────────┐
    │  Вычеты из выручки            │
    │  • Комиссия WB (ppvz_sales_commission)
    │  • Скидки продавца (supplier_promo)
    │  • СПП (ppvz_spp_prc)
    └───────────────┬───────────────┘
                    ↓
    Выручка к зачёту = ppvz_for_pay
                    ↓
    ┌───────────────┴───────────────┐
    │  Расходы                       │
    │  • Доставка (delivery_rub)     │
    │  • Хранение (storage_fee)      │
    │  • Штрафы (penalty)            │
    │  • Приёмка (acceptance)        │
    │  • Эквайринг (acquiring_fee)   │
    │  • Реклама (ad_spend / orders) │
    └───────────────┬───────────────┘
                    ↓
    Чистая прибыль = Выручка к зачёту - Расходы
                    ↓
    Маржинальность = Чистая прибыль / Выручка × 100%
```

### Ключевые метрики

| Метрика | Формула | Описание |
|---------|---------|----------|
| **Чистая прибыль** | `ppvz_for_pay - delivery - storage - penalty - acceptance - acquiring - ad_spend` | Реальный заработок на SKU |
| **Маржинальность %** | `Чистая прибыль / Выручка × 100%` | Доля прибыли в выручке |
| **ROMI** | `(Чистая прибыль - AdSpend) / AdSpend × 100%` | Возврат на вложения в рекламу |
| **CPA** | `AdSpend / Orders` | Стоимость привлечения заказа |
| **Срок окупаемости** | `AdSpend / (Чистая прибыль / Days)` | Дней до окупаемости рекламы |
| **LTV (30 дней)** | `Чистая прибыль × (30 / Days)` | Прогноз прибыли за 30 дней |

## [S4] Визуализация и UI

### Вкладка "Прогноз остатков"

**Компоненты:**
1. **Карточки метрик** — количество товаров по статусам DOS (🔴 < 7д, 🟡 7-14д, 🟢 > 14д)
2. **Таблица** — nm_id, название, текущий остаток, скорость продаж/день, DOS, прогнозная дата запаса
3. **Sparkline** — кривая остатков на 30 дней для каждого товара
4. **Детальный график** — при клике на строку таблицы

**Фильтры:**
- По кабинету (глобальный фильтр)
- По статусу DOS (все / 🔴 / 🟡 / 🟢)
- По артикулу/названию (текстовый поиск)

### Вкладка "Юнит-экономика"

**Компоненты:**
1. **Карточки метрик** — общая прибыль, средняя маржа, ROMI, CPA
2. **Таблица** — nm_id, название, выручка, расходы, прибыль, маржа, ROMI
3. **Детализация** — при клике на строку: полная разбивка расходов
4. **Sparkline** — прибыль по дням для каждого товара

**Фильтры:**
- По кабинету (глобальный фильтр)
- По уровню маржи (все / 🟢 > 20% / 🟡 10-20% / 🔴 < 10%)
- По артикулу/названию (текстовый поиск)
- Сортировка по любой колонке

### Зависимости

- Данные из `Sale` (продажи за 30 дней)
- Данные из `Stock` (текущие остатки)
- Данные из `SalesReport` (финансовая разбивка)
- Данные из `ShelfMetric` (конверсия, выкупы)
- Данные из `AdCampaignStats` (расходы на рекламу)

### Лимиты API

- Расчёт происходит на стороне сервера при запросе
- SQL-запросы агрегируют данные по `nm_id` + `cabinet_id`
- Ограничение 50000 записей на запрос (как в других endpoints)
